# UCPH Staff Tracker: developer guide

How the project works and how to change it. The end-user guide is [README.md](README.md).

## Overview

```
UCPH phone book API ──crawl──▶ data/snapshots/YYYY-MM-DD.csv   (committed; public format)
                                        │
                                   publish (pandas)
                                        ▼
            site/data/*.json, site/data/files/*.xlsx, site/py/matching.py  (built in CI)
                                        │
                              GitHub Pages (static site)
                                        ▼
       browser: tables, downloads, and contact matching in Pyodide (contacts never uploaded)
```

- **The phone book has no hire dates.** New hires are found by comparing snapshots taken
  on different days. A snapshot is taken when someone runs the *Update site* workflow.
- **The site is static.** GitHub Pages serves files only. Anything that needs computing
  is either done in GitHub Actions (`publish`) or in the browser (matching).
- **Matching runs in the browser** with [Pyodide](https://pyodide.org) (CPython compiled to
  WebAssembly), using the same `ku_staff/matching.py` the command line uses. One
  implementation, tested once.

## Repository layout

```
ku_staff/
  __init__.py     version number
  crawler.py      phone book API client -> snapshot CSV (public format)
  staff.py        snapshots, academic categories, exports, new-staff diffs (pandas)
  matching.py     contacts vs UCPH staff matching + Excel output (stdlib + openpyxl ONLY)
  publish.py      builds site/data/ and copies matching.py to site/py/
  cli.py          `ku-staff` command line
site/
  index.html, style.css, app.js   the website (no build step, no frameworks)
  worker.js       Web Worker: loads Pyodide, runs py/matching.py
  vendor/         openpyxl + et_xmlfile wheels (Pyodide doesn't ship openpyxl)
  data/, py/      GENERATED by `ku-staff publish` (gitignored)
data/snapshots/   one CSV per download (committed by the workflow)
tests/
  test_core.py    unit tests (offline)
  test_site.py    browser tests (Playwright + Chrome), marked `browser`
.github/workflows/update-site.yml   download (manual) + build + deploy
```

## Development setup

```bash
git clone https://github.com/enricozano/ucph-staff-tracker.git
cd ucph-staff-tracker
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
python -m playwright install chromium        # only if Google Chrome isn't installed

python -m pytest -m "not browser"            # unit tests, ~1 s
python -m pytest                             # + browser tests (need internet for Pyodide), ~10 s
```

Run the site locally:

```bash
ku-staff --dir data publish site             # build site/data from data/snapshots
python -m http.server -d site 8000           # open http://localhost:8000
```

(Opening `index.html` as a file doesn't work: the worker and `fetch` need http.)

### Command line

```bash
ku-staff [--dir DATA] crawl                  # ~12 min, ~1,000 requests -> DATA/snapshots/<today>.csv
ku-staff [--dir DATA] export [--scope academic|academic_incl_affiliated|all_staff]
ku-staff [--dir DATA] diff --since YYYY-MM-DD [--scope …]
ku-staff [--dir DATA] match CONTACTS.xlsx [--ku FILE] [-o OUT.xlsx] [--sheet S] [--first-col C] …
ku-staff [--dir DATA] publish SITE_DIR
ku-staff [--dir DATA] import-snapshot FILE [--date YYYY-MM-DD]   # old full-format snapshots too
```

`export`, `diff` and `match` write to `DATA/output/`. Excel files there are never
overwritten (`name (2).xlsx`…) because people annotate them.

## The phone book API (`crawler.py`)

<https://about.ku.dk/contact/phone-book/> loads its results from:

```
POST https://www2.adm.ku.dk/selv/pls/!app_tlfbog_v2.soeg
     format=json&startrecord=0&recordsperpage=99&searchstring=<term>
```

| Quirk | Handling |
|---|---|
| A search term is required. | `QUERIES = ["ku.dk", "a", "e", "i", "o", "u"]`, unioned. `ku.dk` alone gives ~21,000 entries; the vowels add ~2,100. |
| Max 99 records per page. | Paginate with `startrecord`. |
| Invalid JSON (raw control characters, unescaped backslashes). | `parse()` repairs it; a page that still fails is refetched record by record. |
| Occasional empty page mid-list. | Retried with backoff, then skipped with a warning. |
| Network errors / site down. | Retries, then `CrawlError` (the workflow run fails; nothing is published). |

Be polite: `DELAY = 0.4` s between requests, about 1,000 requests per crawl.

**If UCPH changes the website**, find the new data URL in the browser's developer tools
(Network tab, while searching the phone book), then update `API`, `fetch_page()` and
`FIELDS`.

### Snapshot format (public)

`data/snapshots/*.csv` is in a **public** repository, so it holds only:
`person_id, first_name, last_name, title_en, title_da, unit_en, department, subunit,
faculty, research_profile, email_sha256`. No phones, addresses or plain emails.
`email_sha256` (SHA-256 of the lowercased work email) lets the matcher detect "already at
UCPH" by comparing hashes. Don't add personal fields here.

`import-snapshot` converts the original full format (with plain `email`, `phone`…) into
this one.

## Academic categories (`staff.py`)

`categorize(title)`: first match wins in `CATEGORIES`, a list of `(name, is_core, regex)`.
Core categories: Assistant/Associate/Professor, PhD, Postdoc, Researcher / Research
assistant, Lecturer, Academic staff (unspecified). Affiliated: Emeritus, Guest / visiting /
external, Teaching assistant / instructor. `NON_ACADEMIC` excludes support roles
("Academic Officer", "PhD Administrator"…) unless the title says "professor". Order
matters: Emeritus and Guest come before Professor, and Professor before PhD. Add a case
to `test_categorize` for every change.

## New staff (`staff.new_staff_table`)

Compares the latest snapshot with the one taken on or before a date, **within scope**:
someone who was a master student and is now a PhD fellow counts as new
(`previous_title` = "Master Student"). `publish` precomputes this for every earlier
snapshot (`data/new-since-<date>.json` + Excel files).

## Matching (`matching.py`)

**Constraint: this module runs in Pyodide.** Standard library and openpyxl only. No
pandas, no imports from other `ku_staff` modules. `test_publish_builds_site_data` checks
the copy in `site/py/`, and the browser tests run it for real.

1. `canon()` normalizes names: lowercase, no accents, ø→o, æ→ae, then oe→o, aa→a, ae→a.
2. Candidates: same (first given name, last surname token). `compare_names()` accepts
   identical names (`full name`) or one being a subset of the other (`partial name`);
   contradicting names (different middle names) never match.
3. `already_ucph_at_signup`: same work email (hash), or any ku.dk email in the contacts
   file.
4. Confidence: see the module docstring. It's also the *method* sheet of the Excel, so
   keep it accurate.
5. Contacts file: `read_table()` (xlsx via openpyxl read-only, or CSV with delimiter
   sniffing). HubSpot writes a wrong sheet size, hence `ws.reset_dimensions()`.
   Duplicate headers get `.1` suffixes. Columns are guessed from `COLUMN_GUESSES`.

`compare()` is the shared core. The CLI calls `run()`; the website's `worker.js` calls
`compare()` through a small Python glue function and returns the Excel bytes to the page.

Reference result (HubSpot export of 16,885 leads vs the 2026-10-23 snapshot): 41 pairs
(12 High, 9 Medium, 20 Low) and 3 already at UCPH. It takes ~9 s in CPython and ~15–20 s
in the browser (including loading Pyodide the first time).

## The website (`site/`)

- Plain HTML/CSS/JS; no build step. All data goes into the page with `textContent`, never
  `innerHTML` (names come from external sources).
- `app.js` reads `data/index.json` first; tables render 100 rows at a time.
- `worker.js` loads Pyodide from the jsDelivr CDN (version pinned in `PYODIDE`) and the
  wheels in `site/vendor/` (names pinned in `WHEELS`). The worker starts loading when the
  Compare tab opens. When upgrading Pyodide or openpyxl, update both constants and run
  the browser tests.
- `<meta name="robots" content="noindex">` keeps the site out of search engines.

## Updating and deploying (`.github/workflows/update-site.yml`)

- **Run workflow** (manual): tests → crawl → commit the snapshot → `publish` → deploy to
  Pages. A failed crawl stops the run, so nothing is committed or deployed.
- **Push to main**: tests → `publish` → deploy (no crawl).
- Pushes made by the workflow itself don't trigger another run (GitHub rule), so there's
  no loop.
- One-time setup: *Settings → Pages → Source: GitHub Actions*. Pushing workflow files
  needs a token with the `workflow` scope (`gh auth refresh -h github.com -s workflow`).

## Privacy rules for contributors

- This repository is **public**. Never commit contact exports, match results or anything
  derived from our CRM. `.gitignore` blocks the usual names (`hubspot-crm-exports-*`,
  `*contacts*`, `output/`).
- Snapshots stay in the public format (no phones, addresses, plain emails).
- Contact files are processed only in the browser. Don't add any upload, analytics or
  logging of them.

## Known limitations and ideas

- New-hire dates are only as precise as the interval between downloads.
- Name matching finds namesakes, and misses nicknames ("Kate"/"Katherine") and
  transliteration variants. A nickname table or fuzzy first-name matching would help, at
  the cost of more false positives.
- Leavers and promotions aren't reported (easy to add in `staff.py` + a new tab).
- The crawl takes ~12 min because of the polite delay and 6 queries.
- GitHub's servers could be blocked by UCPH's firewall. If manual runs keep failing while
  the phone book works in a browser, run `ku-staff --dir data crawl` locally and push the
  new snapshot instead.
